# aSAH Dashboard

An interactive, web-based dashboard for the analysis and visualization of clinical
course data of patients with **aneurysmal subarachnoid hemorrhage (aSAH)**. It
presents the intensive-care course of a single patient across the whole stay:
physiological time series, derived measures such as the cerebral perfusion
pressure (CPP), laboratory values, admission scores, complications and outcome,
all on a common relative time axis.

The project is split into a **Python/FastAPI backend** that ingests, prepares and
serves the data over a REST API, and a **React/TypeScript frontend** that renders
the interactive visualizations with Vega-Lite. Data can be loaded from a fixed
local dataset or uploaded as CSV files at runtime.

> **Note on data:** The clinical CSV files are real, pseudonymized patient data.
> They live in `backend/data/` and are **git-ignored and must never be committed**
> (see [Data](#data)). All screenshots and shared examples use synthetic data.

## Run Locally

The backend and the frontend run as two separate processes. Start the backend
first, then the frontend.

### Backend

Requires Python 3.11+ .

```bash
cd backend
python -m venv .venv
# Windows:  .venv\Scripts\activate
# Linux/Mac: source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

The API is then available at `http://localhost:8000`. Interactive API
documentation (generated by FastAPI) is at `http://localhost:8000/docs`.

On startup the backend loads the dataset from `backend/data/` into memory. If a
Parquet cache exists in `backend/data/cache/`, it is loaded directly; otherwise it
is built once from the CSV files. If no dataset is present, the app still starts
and waits for a CSV upload.

### Frontend

Requires Node 20+ .

```bash
cd frontend
npm install
npm run dev
```

This starts the Vite dev server (by default at `http://localhost:5173`). The
frontend expects the backend at `http://localhost:8000`; this origin is allow-listed
for CORS in `backend/app/config.py`.

## General Structure

The application follows a three-tier client-server design:

```
CSV / Parquet  →  Backend (FastAPI + pandas)  →  REST/JSON  →  Frontend (React + Vega-Lite)
```

The **backend** owns data holding and preparation. The heavy work (validation,
relative time axis, plausibility filtering, temporal aggregation, CPP derivation)
happens on the server, close to the full data, so that only the small, requested
and already condensed slice is sent to the client. The prepared tables are held
entirely **in memory**; no database is used.

The **frontend** is a single-page application. It fetches condensed data per
patient and renders it with Vega-Lite. All state (selected patient, active
filters, chosen parameters, language) lives in the browser.

Programming languages: **Python** (backend) and **TypeScript** (frontend). Code,
identifiers and comments are in English; the user interface can be switched
between German and English.

## Back End

The backend code is in `backend/app/`. It is a FastAPI application composed of a
preparation module, an in-memory data store and a routing layer.

```
backend/app/
  main.py            FastAPI app, startup/lifespan, CORS, meta endpoints
  config.py          paths, parameters, plausibility bounds, thresholds, defaults
  models.py          Pydantic response models (typed API schemas)
  preprocessing.py   build_frames(): raw CSV -> three internal tables
  data_loader.py     DataStore ("store"): in-memory tables + queries
  routers/
    patients.py      per-patient endpoints (summary, timeseries, labs, ...)
    dataset.py       dataset status, CSV upload, reset
```

### Data Preparation Pipeline

`preprocessing.build_frames()` turns the raw files into three internal tables
(a wide **patient table**, and long-format **physiological** and **laboratory**
tables). The steps run in a deliberate order:

1. **Read + verify.** Each file is read and checked for the required columns. For
   the time-series files (physiological, laboratory) the columns case, parameter/
   analyte, timestamp and value must be present; for the others at least the case
   id. A missing required column aborts preparation with a clear error message
   (raised as `ValueError`, surfaced by the API as HTTP 400).
2. **Type coercion.** Values are converted to numeric or datetime types.
   Non-convertible entries become missing values, and time-series rows without a
   valid case id or timestamp are dropped.
3. **Relative time axis.** For each patient the earliest measurement (across
   physiological and laboratory data) is defined as day 0; all timestamps are
   converted to "days since admission". The first and last measurement also yield
   the stay duration.
4. **Plausibility filtering.** Physiological values outside fixed per-parameter
   bounds (`config.PLAUSIBILITY`) are marked invalid and excluded from display.

Temporal **aggregation** and the **CPP derivation** are performed at query time in
the data store (see below), not baked into the stored tables, so the raw
resolution stays available and the derived CPP stays consistent with MAP and ICP.

### Data Store

`data_loader.py` defines a `DataStore` (the module-level singleton `store`) that
holds the three prepared tables in memory and answers all queries:

- `load_demo()`: load the fixed dataset from the Parquet cache, or build it once
  from the CSV files in `backend/data/` and cache it.
- `load_frames(...)`: replace the in-memory tables with an uploaded dataset
  (session-based, not persisted to disk).
- Query helpers used by the routers: `list_patients`, `patient_summary`,
  `timeseries` (with aggregation `raw | hour | day` and CPP derivation),
  `labs`, `available_labs`, `complications`, `outcome`, `info`.

**Aggregation.** For `hour`/`day` the time axis is split into fixed-width bins
(one twenty-fourth of a day, or one day) and the mean of the valid values is taken
per bin and parameter. **CPP** is derived per timestamp as `CPP = MAP (BPMean) − ICP`
from the aggregated values.

### Files

- `backend/data/`: the five input CSV files (see [Data Formats](#data-formats)).
  **Git-ignored**, holds the real primary data.
- `backend/data/cache/*.parquet`: the prepared tables, cached as columnar Parquet
  so they need not be rebuilt on every start. Also git-ignored.
- `backend/requirements.txt`: pinned Python dependencies.

### Configuration

All fixed defaults live in `backend/app/config.py` and can be adjusted in one
place:

- `VITAL_PARAMS`: the eight physiological parameters
  (`HF, SPO2, BPSystolic, BPDiastolic, BPMean, ICP, RR, T`).
- `DERIVED_PARAMS`: parameters derived at runtime (`CPP`).
- `PLAUSIBILITY`: per-parameter lower/upper bounds for the plausibility filter.
- `THRESHOLDS`: clinically critical thresholds highlighted in the charts
  (`ICP > 22`, `SPO2 < 90`, `CPP < 60`, `T > 38.3`). **Mirror only.** The
  highlighting happens entirely in the client, so the authoritative copy is
  `THRESHOLDS` in `frontend/src/constants.ts`; no backend code reads this one.
  Keep both in sync, and change the frontend copy when adjusting a threshold.
- `DEFAULT_LABS`: the pre-selected laboratory analytes.
- `RESOLUTIONS` / `DEFAULT_RESOLUTION`: `raw | hour | day`, default `hour`.
- `ALLOWED_ORIGINS`: CORS allow-list (the frontend dev server).

## Front End

The frontend code is in `frontend/src/`. It is a Vite + React 19 single-page
application written in TypeScript.

### Layout

The interface is a three-column layout below a persistent header:

- **Header**: patient search/select, data import, language switch.
- **Left column**: the filter panel (cross-filter histograms + parameter
  selection).
- **Center column**: the charts (vital courses and the MAP/ICP dual-axis chart).
- **Right column**: the status and patient-summary panels.

The two side columns can be collapsed to a narrow strip and resized by dragging
their inner edge; charts adapt their width automatically.

### Visualizations

All charts are built with Vega-Lite. The recurring building blocks are:

- **Small Multiples**: the selected vital parameters are shown as equally scaled
  line charts stacked on top of each other (`VitalsPanel` + `SeriesChart`), so the
  individual courses stay readable and vertically comparable at a given time.
- **Dual-Axis**: MAP and ICP are drawn in one coordinate system with two
  independent y-axes (`DualAxisChart`), so the very different value ranges stay
  legible. The vertical gap between the curves indicates qualitatively how
  MAP − ICP develops. Because the two y-scales are independent, it cannot be read
  off quantitatively; CPP is available as its own parameter for that.
- **Threshold highlighting**: measurement points beyond a configured threshold
  (ICP, SPO2, CPP, temperature) are colored, and the threshold itself is drawn as
  a dashed rule. Parameters without an entry in `THRESHOLDS` are drawn without a
  rule.
- **Gap handling**: real measurement gaps break the line instead of being bridged
  silently. Before rendering, `insertGaps` (`SeriesChart`) and `insertGapsMulti`
  (`DualAxisChart`, per parameter) insert a point with `value: null` wherever the
  distance between two consecutive measurements exceeds
  `max(median spacing × 3, 0.25 days)`. Vega-Lite interrupts a line exactly at
  null values. The median term adapts the threshold to how densely a series is
  sampled (vitals vs. laboratory), the lower bound keeps small delays from
  fragmenting the line. Short gaps are still bridged.
- **Cross-filter histograms**: the cohort filter in `FilterPanel` shows the case
  counts per age decade, Fisher, modified Fisher, WFNS and aneurysm location as
  linked bars.

### Interactions

- **Parameter selection**: checkboxes choose which vital parameters are shown.
- **Time-window zoom (Overview + Detail)**: each chart has a slim overview strip;
  dragging an interval (brushing) on it sets the x-domain of the detail chart
  below, while the overview keeps the whole stay in view.
- **Expand**: any chart opens in a large modal detail view via `ChartCard`.
- **Details on demand**: hovering a measurement point shows a tooltip with the
  exact day and value.
- **Cross-filter**: clicking a histogram bar toggles the corresponding cohort
  filter; the other histograms update accordingly.

### Internationalization

The whole interface, including axis and tooltip labels, can be switched between
German and English. All texts are resolved through a single lookup
(`useLanguage()` / `translations.ts`), and the chosen language is stored in the
browser and restored on load. New texts are added in `translations.ts` only.

## REST API

All endpoints return JSON. For the time series, the desired parameters and the
resolution can be given as query parameters.

| Method & Endpoint | Purpose |
| --- | --- |
| `GET /patients` | list of all patients (short attributes) |
| `GET /patients/{id}` | summary (scores, complications, outcome) |
| `GET /patients/{id}/timeseries?params=&resolution=` | physiological time series (`params` = comma list, `resolution` = `raw\|hour\|day`) |
| `GET /patients/{id}/labs?analytes=` | laboratory time series (optional analyte list) |
| `GET /patients/{id}/labs/available` | analytes available for this patient |
| `GET /patients/{id}/complications` | complication labels |
| `GET /patients/{id}/outcome` | outcome / mortality labels |
| `GET /dataset/status` | status of the loaded dataset |
| `POST /dataset/upload` | upload own CSV data (multipart; clinical file required, others optional) |
| `DELETE /dataset` | return to the fixed dataset |
| `GET /health` | health probe (`{status, patients}`) |
| `GET /` | API info + link to `/docs` |

The uploaded files are processed through the same preparation pipeline and used
without being persisted to disk.

## Used Libraries

### FastAPI + pandas

The backend uses **FastAPI** to build the REST interface. It validates endpoint
in- and outputs against typed schemas (Pydantic) and generates interactive API
documentation automatically. The tabular preparation and querying is done with
**pandas**, and the prepared tables are cached as **Parquet** (columnar, compressed)
so they load faster than the raw CSV and need not be rebuilt on every start.

### React + Vite + TypeScript

The frontend is a single-page application built with **React** and **TypeScript**,
bundled by **Vite**. It is split into reusable components (see above).

### Material UI

**Material UI** provides the interactive UI components: Autocomplete (patient and
analyte selection), Button, Checkbox (parameter selection), Slider (age filter),
TextField, ToggleButtonGroup (language), as well as AppBar, Paper, Dialog, Chip and
layout components. A central theme defines the color scheme (a muted blue, with a
strong red reserved for critical values).

### Vega-Lite + React-Vega

**Vega-Lite** is a declarative, JSON-based grammar for interactive visualizations
that compiles to Vega. Three composition means are central here: `layer` (stack
marks in one coordinate system), `vconcat` (stack the overview strip above the
detail chart) and `resolve` (share the x-axis while keeping y-axes independent, as
in the MAP/ICP dual-axis chart). Interaction is expressed through *selections*; an
interval brush on the overview strip supplies the x-domain of the detail chart.
**React-Vega** embeds these specifications into the React components.

## Code Style

Code, identifiers, file names and commit messages are English. **Inline comments
are German** and explain *why* a decision was made rather than what a line does.
They are deliberately sparse and sit where the code is not self-explanatory, for
example the gap threshold in `insertGaps`, the floor-based binning in
`_aggregate`, the independent y-scales in `DualAxisChart`, or the `except`
argument that makes the cross-filter work.

The response models in `backend/app/models.py` are the one exception: they carry
Python **docstrings** instead of `#` comments. FastAPI reads those and writes them
into the generated OpenAPI schema, so they are visible as field descriptions at
`http://localhost:8000/docs`. A `#` comment in the same place would not be.

## Data

The dashboard does not retain any data on disk beyond the (git-ignored) local
dataset and its cache. Uploaded datasets are held in memory only and are discarded
when the process stops or a new dataset is loaded.

**The clinical CSV files are real, pseudonymized patient data.** They live in
`backend/data/` (git-ignored) and are governed by a signed data-protection
agreement. They must never be committed, and screenshots or shared examples must
use synthetic data.

### Loading Data

There are two ways to get data into the dashboard. Both run through the same
preparation pipeline.

**1. As a fixed local dataset.** Put the CSV files into `backend/data/`, using
exactly these file names:

```
backend/data/
    clinical_demog_dataset.csv          (required)
    physiological_dataset.csv           (optional)
    laboratory_dataset.csv              (optional)
    targets_complications.csv           (optional)
    targets_mortality_funcoutcome.csv   (optional)
```

On the first start the backend builds the three internal tables from these files
and caches them as Parquet in `backend/data/cache/`; every later start reads the
cache directly. Rebuild it by deleting the cache folder, or by running
`python -m app.preprocessing --force` from `backend/`. If the folder is empty the
app still starts and waits for an upload.

**2. By uploading at runtime.** Click **Load data** in the header. The dialog
offers one field per input class, again with only the clinical file required. The
uploaded data replaces the current dataset **in memory only** and is never written
to disk, so it is gone when the process stops. `DELETE /dataset` switches back to
the fixed local dataset.

The second way is the one to use for demonstrations and screenshots, since it
lets you work with synthetic data without touching `backend/data/`.

### Data Formats

The input consists of five CSV files, linked by the case id (`CaseId`). Only the
clinical/demographic file is required for an upload; the others are optional.

**Clinical / demographic** (`clinical_demog_dataset.csv`)

```
CaseId, Age, Sex, Intervention, AneurysmLocation, WFNSCategory, Fisher, mFisher
```

`Sex` is `female`/`male`, `Intervention` is `coiling`/`clipping`,
`AneurysmLocation` is `anterior`/`posterior`, and `WFNSCategory` is dichotomized as
`good`/`poor`. `Fisher` and `mFisher` are the (modified) Fisher grades.

**Physiological** (`physiological_dataset.csv`): long format

```
CaseId, Timeseries, Timestamp, Value
```

`Timeseries` is one of the vital parameters (`HF, SPO2, BPSystolic, BPDiastolic,
BPMean, ICP, RR, T`), `Timestamp` is an absolute timestamp, `Value` the measured
value.

**Laboratory** (`laboratory_dataset.csv`): long format

```
CaseId, Timeseries, Timestamp, Value, Unit
```

Like the physiological file, plus the `Unit` of the analyte. Reference ranges are
not part of the data.

**Complications** (`targets_complications.csv`): binary labels

```
CaseId, Vasospasm, DCI, DelayedInfarction, Epilepsy, MyocardialInfarction, Hydrocephalus, Infections
```

**Outcome / mortality** (`targets_mortality_funcoutcome.csv`): binary labels

```
CaseId, MortalityDischarge, Mortality6M, FunctionalOutcomeDischarge, FunctionalOutcome6M
```

Files are read as UTF-8 (with BOM tolerated). Complication and outcome labels are
encoded as `1` (present) / `0` (absent).

### Relative Time Axis

Physiological and laboratory values carry an absolute timestamp, but the data
contains no admission date. For each patient, day 0 is therefore defined as the
earliest measurement across the physiological and laboratory data, and all
timestamps are expressed as "days since admission". Scores, complications and
outcome are static, per-patient labels without a timestamp.
